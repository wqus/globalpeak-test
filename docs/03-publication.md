# 03 / Модуль автопубликации → GP OS

## Граница реализации

Работают локальный HTTP-сервер, тестовые GET/PATCH карточки, SQLite-очередь, проверка полей, оптимистическая версия, одобрение конкретного содержания, защита от дублей, отложенный повтор, сверка неопределённого исхода, обработка отказа и запись результата обратно в тестовую карточку. Внешний адаптер подменён таблицей `fake_remote`. Ссылка `example.invalid` заведомо не является объявлением. Реальных отправок, ключей и расходов нет.

Исходные файлы `stage-2-types.ts` и реализации маршрутов не предоставлены. Известные факты о GP OS взяты только из задания: UUID/версия, достоверность и конфликты, advertising, GET/PATCH, авторизация, CSRF, expectedVersion и 409. Любые формы ниже — предлагаемый контракт, а не проверенная структура production.

## Один объект

Учебный UUID `c4b69f48-2ab2-43ed-9d90-976ba62bf001`, версия 7, 118 м² и вымышленная цена 24 млн ₽. Это другой, полностью синтетический объект, не объект «Вкусно — и точка».

1. GP OS выдаёт карточку, факты со статусом подтверждения, текст, ссылки на фотоактивы и согласование содержания. В demo `GET /api/properties/{id}` защищён временной локальной сессией.
2. Проверяются подтверждённые адрес, площадь, цена, категория и сделка, отсутствие конфликтов, описание, фото и подтверждение прав. Согласование связано с хешем содержания: изменение цены требует нового одобрения. Точный набор обязательных полей Авито зависит от схемы категории и ещё не проверен.
3. `POST /api/publications` с `{propertyId, expectedVersion}` создаёт одну задачу. Повтор для тех же данных возвращает существующую. Уникальная привязка `(property_id, channel, account)`, постоянный внешний Id и хеш содержания. Версия GP OS меняется и из-за служебных статусов, поэтому её нельзя использовать как единственный ключ объявления.
4. Worker повторно проверяет хеш перед отправкой: если карточка поменялась, задача `superseded`. Тестовое принятие даёт `submitted`, без ссылки. Лишь отдельный отчёт модерации переводит её в `published`.
5. Результат PATCH-ится в `advertising.avito` с `expectedVersion`. При 409 внешний результат остаётся сохранённым, `sync_status=conflict`; перечитать карточку, объединить только блок advertising и повторить PATCH. Новая отправка на Авито для исправления записи в GP OS не нужна.

## Предлагаемые интерфейсы

| Направление | Поля / маршрут | Проверка |
|---|---|---|
| GP OS → модуль | `id`, `version`, факты `{value, verification, conflict, source}`, описание | UUID, expectedVersion, типы, допустимые значения, достоверность |
| GP OS → модуль | `images[{asset_id, mime, width, height, rights_confirmed}]` | Наличие актива, права, допустимость формата; реальные байты в demo не скачиваются |
| GP OS → модуль | `approval{approved, by, for_content_hash}` | Авторизованное согласование именно этой версии содержания |
| Модуль → GP OS | `advertising.avito{id, status, content_hash, source_version, external_id?, url?, error?, updated_at?}` | Идентификатор попытки/операции, ожидаемая версия, частичный PATCH |
| Браузер → модуль | `POST /api/publications`, `GET /api/publications/{id}` | Сессия, CSRF для записи; 202 — очередь, 200 — существующая задача |
| GP OS → worker, предложено | Событие `property.advertising.approved` или polling outbox | Подпись, уникальный event_id, повторяемая доставка, журнал потребления |
| Файлы, предложено | `GET /api/properties/{id}/images`, затем короткоживущий signed URL по asset_id | Доступ только к фото данного объекта, TTL, хеш, MIME, размер |

Последние два интерфейса не реализованы, их нужно согласовать. В demo возврат содержит id/status/url/error/hash/version; `external_id` есть в записи очереди. Поля updated_at, request_id, внешний отчёт и их добавление в GP OS — задачи production-адаптера.

В production изображения модуль получает через service-to-service доступ, проверяет тип по содержимому и размер, не доверяет произвольному URL из карточки. Чтобы Авито могло забрать фото, нужен согласованный механизм разрешённых HTTPS-ссылок с достаточным TTL или загрузки файла, если это поддержано схемой. Не публиковать внутренние URL, токены GP OS и signed URL в логах. Входные URL для скачивания — allowlist; иначе появляется SSRF. Для смены приватности фото предусмотреть отзыв доступа.

## Разрешённый путь Авито

Предпочтение: официальная автозагрузка по согласованному формату категории «Коммерческая недвижимость» и разрешённое получение отчётов/статусов через доступный API или кабинет. До реализации подтвердить у владельца аккаунта возможность подключения, тариф/категорию, права API, лимиты, правила дублей, семантику обновления и снятия. Не проектировать публикацию на основе UI-бота или недокументированного запроса.

Официальные страницы автозагрузки и API найдены как точки входа, но не открылись в среде проверки. Поэтому XML не выдаётся за проверенный Avito XML, поля категории не объявлены окончательными, конкретный HTTP endpoint создания не придуман, тариф и лимиты не указаны как факт. Demo работает на внутреннем JSON-контракте.

Если автозагрузка оперирует полным фидом аккаунта, формировать его из всей активной подтверждённой выборки атомарно. Ошибка одной карточки не должна удалить остальные объявления. Сохранить предыдущий принятый фид и проводить diff перед заменой. Семантику отсутствующей строки и удалений выяснить до пилота. При миграции существующих объявлений сначала сопоставить внешние ID; создавать новые без сверки нельзя.

Постоянный Id (`gp-{UUID}` в учебной модели) не менять при новой цене, тексте или повторе отправки. Дополнительная защита — уникальная привязка объекта, аккаунта и канала; сначала сверка активных объявлений аккаунта. На стороне сервиса нельзя гарантировать отсутствие любых исторических дублей без доступа к этому инвентарю.

## Ошибки, повтор и согласованность

| Событие | Действие |
|---|---|
| Неподтверждённая цена / конфликт адреса | 422, список полей; никаких внешних операций |
| Устаревший expectedVersion | 409, перечитать; не затирать изменения |
| Временная недоступность / 5xx | `retry_wait`, 30/60/120 сек + jitter до 5 сек; максимум 3 отправки, затем ручная очередь |
| 429 в production | Учесть Retry-After и лимит аккаунта; это пока только проектное требование |
| Таймаут после возможного принятия | `reconciling`; искать по постоянному Id до повтора, не создавать новый Id |
| Отказ категории/модерации | `rejected`, понятная ошибка; автоматический повтор без исправления бессмыслен |
| Отправлено, но нет отчёта | Оставить `submitted`; проектный таймаут ожидания 30 мин → эскалация, реальный SLA согласовать |
| Конфликт записи результата в GP OS | Сохранить внешний результат и повторить только синхронизацию |
| Отзыв ключа / недостаток прав | Приостановить канал, уведомить ответственного, не повторять бесконечно |

Доставку в production проектировать at-least-once, а операции — идемпотентными. Локальная SQLite-транзакция включает fake-адаптер и потому не доказывает атомарность реального внешнего вызова. Для нескольких production-worker нужны PostgreSQL outbox + lease/блокировка задачи, сетевой вызов вне транзакции, затем запись результата; crash после отправки обрабатывается сверкой. В demo очередь переживает перезапуск, конкурентные enqueue проверены, но настоящий распределённый сбой не воспроизведён.

## Настройки и секреты

Настройки без секретов: аккаунт/канал, mapping категории, лимиты, расписание, включённость канала, ответственный, версия шаблона, feature flag dry-run. Секреты: secret manager с разграничением ролей, минимальные scopes, ротация и отзыв; отдельный тестовый контур. OAuth/другую схему не выбирать до документации аккаунта. Логи содержат request_id и коды ошибок, не токены, URL с секретами, контакты и весь текст карточки.

Для браузера GP OS сохранить действующую сессию и CSRF. Для фонового worker согласовать сервисную авторизацию; не переносить CSRF-токен пользователя в cron. Demo использует случайные cookie/CSRF в памяти, привязан к 127.0.0.1 и проверяет Origin/Host. Это локальная защита демонстрации, не production-аутентификация GP OS. Файл .env, runtime БД и ключи в Git не добавляются.

## Что проверено / что нужно

Сейчас можно воспроизвести 7 сценариев: успех, валидация, временная ошибка с повтором, неопределённый исход со сверкой, 409, обновление того же объявления, постоянный отказ. Тесты также проверяют смену карточки до отправки, исчерпание повторов, рестарт очереди, конкурентную постановку, auth/CSRF и HTTP-контракты.

Нужно от GP OS: точный stage-2-types.ts, OpenAPI/маршруты, структура advertising, семантика частичного PATCH, способ сервисной авторизации, разрешения на служебную запись, структура медиа, правила согласования и аудита, webhook/outbox или polling. От Авито: доступ аккаунта и категории, текущая схема/валидатор, тестовая возможность/безопасный dry-run, правила Id/AvitoId/миграции, отчёт и статусы, лимиты, SLA, фото и удаления. Production-доступ для этого тестового не нужен.

## План и оценка

| Этап | Часы | Календарь |
|---|---:|---|
| Согласовать контракты, доступы и mapping категории | 8–12 | 1–2 рабочих дня + внешнее ожидание |
| Получение карточки/фото, валидация и одобрение | 10–14 | 2 дня |
| Outbox, постоянные ID, официальный адаптер и отчёты | 14–22 | 2–3 дня |
| Повторы, синхронизация 409, журнал и эксплуатация | 8–12 | 1–2 дня |
| Приёмка и контролируемый пилот владельцем аккаунта | 4–8 | 1–2 дня |

44–68 ч, 7–11 рабочих дней после доступов, один разработчик; GP OS-разработчик 4–8 ч и владелец аккаунта 2–3 ч включены в оценку труда, если предоставлены в рамках команды. При отсутствии схемы GP OS нужен отдельный пересчёт. По условной ставке 2 500 ₽/ч: 110–170 тыс. ₽.

Эксплуатация: доля инфраструктуры 0,5–1,5 тыс. ₽/мес., сопровождение 4–6 ч (10–15 тыс.) + **A — действующая стоимость тарифа/размещений Авито**, которую должен подтвердить владелец аккаунта. Рекламное продвижение сверх размещения не включено. Лимиты и стоимость публикаций неизвестны; «бесплатную интеграцию» обещать нельзя. В тестовом — 0 новых платных запусков.
